### 2. Why the audio never landed — and why this was always going to take several days

Not a bug. A quota the batch is simply larger than.

`lib/db/seed-audio.ts:6-16` documents it: the free Gemini TTS tier allows **100 requests per day per model**,
and the counter is **shared by every mode** (`words`, `narrations`, `dialogues`, `phrases`). 144 mnemonics
cannot be voiced in one day, so a single seeding run was always going to stop short by at least 44.

The recent hardening here is working as intended and makes the recovery cheap:

- `9498446` *"fix(audio): stop at the daily TTS cap instead of burning 175 doomed calls"* — `rethrowIfDailyQuota`
  (`:19-28`) detects the `per_model_per_day` 429 and aborts the run rather than issuing every remaining call
  against a spent quota.
- The seeders **skip rows that already have audio**, so runs resume exactly where the last one stopped
  (`:13-15`). Re-running is safe and idempotent; nothing is redone or double-billed.

**Action — needs a human at a real machine.** This is the one genuinely actionable item tonight and the sandbox
cannot do it: reaching Neon and the TTS API both require hosts the proxy blocks. Run on consecutive days until
the count reaches 0:

```
npm run db:seed-audio -- --mode=words --lang=pt
```

At 100/day shared across modes, budget **2–3 runs** (more if narrations/dialogues compete for the same quota
that day). Verify by watching `stuckMnemonicsLast72h` fall in the next digests — it should drop by roughly the
number of calls each run completed.

### 4. New, minor: `production_close_correct` lands in a phantom cue row

Reading `CUE_FROM_EVENT` (`lib/db/pedagogy-queries.ts:28-35`) against the emitters turned up a labelling
wrinkle worth recording before it bites.

`ProductionTyping.tsx:106-109` fires `production_close_correct` when an answer is accepted within fuzzy
tolerance. That event name hits the `ELSE` branch, `regexp_replace(event, '_(correct|wrong|attempt)$', '')`,
which strips only the trailing `_correct` → cue type **`production_close`**. Consequences:

- It becomes its own row on `/admin/pedagogy`, one that can never contain a `_wrong` event and therefore always
  reads **100%** accuracy.
- The attempt disappears from the `production` denominator entirely — not just from its numerator.

The separation is *partly* deliberate: `lib/pedagogy/telemetry.ts` says the event exists "so it doesn't inflate
the production accuracy it isn't evidence of." But that intent is served by keeping the attempt in the
denominator and out of the numerator, not by moving it into a separate 100% row. This is exactly the shape
`CLAUDE.md` warns about under Measurement — a row that reads as a real measurement and isn't one.

**Zero current numerical impact**: no `production_close` row appears in any digest, meaning no answer has been
fuzzy-accepted in 30 days. Logged as latent, not urgent. A human should decide the intended denominator before
anyone changes the regex.
